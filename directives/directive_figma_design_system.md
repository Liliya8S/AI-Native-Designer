# Директива: Дизайн-система через Figma MCP

Дополняет `directive_figma_mcp.md` (там — механика вызова MCP-инструментов). Здесь — что в этом проекте считать «дизайн-системой» на текущей стадии и как с ней работать.

---

## 0. Реальное состояние проекта (важно прочитать перед работой)

**Это не репозиторий с кодом продукта.** Это research/discovery-репозиторий для мобильного приложения «AI Native Driving Assistant» (офлайн-тесты ПДД + распознавание знаков on-device, см. `prd.md`). В корне нет `package.json`, нет фронтенд-фреймворка, нет компонентов, нет CSS, нет иконок, нет токенов — только:

- **Продуктовые артефакты**: `brief.md`, `prd.md`, `personas.md`, `features_list.md`, `mvp_scope.md`, `hypotheses.md`, конкурентный анализ (`competitive_analysis*.md`), интервью (`interview_*.md`)
- **UX-аудит конкурента**: `Audit/audit_report.md` + `Audit/user_flow.md` + 11 скриншотов в `Audit/Screens/*.jpg` — это скриншоты **чужого** приложения (Drom PDD), взятые для эвристической оценки. Не путать с ассетами собственного продукта.
- **Агентная архитектура**: `directives/` (SOP) + `execution/` (детерминированные Python-скрипты) + `.tmp/` (промежуточные файлы, не коммитятся) — см. `directives/Claude.md` за полным описанием 3-слойной архитектуры.

**Следствие для Figma-работы**: сейчас нет кода, из которого можно вытащить существующие токены/компоненты. Направление работы — **от продукта к дизайну** (PRD → персоны → Figma design system → мокапы), а не «от кода к Figma» (Code Connect, реверс токенов из CSS и т.п. — пока неприменимо).

**Платформа не выбрана.** PRD (`prd.md`, §7) требует iOS + Android, офлайн-режим, on-device ML — но фреймворк (React Native / Flutter / нативный Swift+Kotlin) не зафиксирован ни в одном документе. Не подставляй React/CSS-переменные/Tailwind и т.п. по умолчанию — задай вопрос или держи всё, что создаёшь в Figma, платформенно-нейтральным.

Когда появится отдельный репозиторий с реализацией — **обязательно перезапусти `create_design_system_rules`** уже на нём, чтобы получить реальные разделы про токены/компоненты/иконки. Этот файл описывает только текущую, до-имплементационную стадию.

---

## 1. Токены (Design Tokens) — статус: не созданы

Токенов (цвета, типографика, spacing) в коде нет — их ещё нет и в Figma. Когда будешь создавать дизайн-систему с нуля через `use_figma` / `figma-generate-library`:

- Создавай **Figma Variables** (не просто стили) — они платформенно-нейтральны и переживут любой выбор фреймворка.
- Структура: primitive-токены (raw values: `blue.500`, `space.4`) → semantic-токены (`color.action.primary`, `space.gap.md`), стандартная двухуровневая модель.
- Источник значений на этой стадии — не существующий код, а: brand/tone из `brief.md` и `personas.md`, и ограничения доступности из PRD §7 («минимальный contrast ratio для основных кнопок», «voice-first / hands-free»).
- Не изобретай палитру без опоры на референсы — если нет брендбука, используй `Audit/audit_report.md` (конкурентный аудит) как отправную точку для паттернов, но не копируй чужой брендинг.

## 2. Компонентная библиотека — статус: не создана

Нет ни одного UI-компонента в коде. При построении в Figma:
- Начинай с компонентов, которые PRD называет обязательными (`prd.md`, §5 Must Have): карточка билета/теста, экран камеры с индикатором уверенности, TTS-сводка/карточка результата, очередь повторения, бейдж приватности, онбординг.
- Используй variants (Figma component properties) для состояний, которые уже зафиксированы в аудите: `default / selected / error / empty` — см. найденные в `Audit/audit_report.md` проблемы с empty-state (0/0) и отсутствием active-состояния как готовый список состояний, которые обязаны быть явно спроектированы (не повторять чужие ошибки).
- Никакого Storybook/аналогов — их создавать рано, пока нет кода-потребителя.

## 3. Фреймворк и стилизация — не определены

Не предполагай ничего. Если в задаче требуется знание фреймворка (например, для Code Connect маппинга компонент↔код) — это заблокировано, пока команда не выберет стек. Пока: работай только в Figma-слое, без code-side допущений.

## 4. Ассеты — статус: только референсные скриншоты конкурента

`Audit/Screens/01_PDD.jpg` … `11_PDD.jpg` — 11 скриншотов конкурентного приложения, использованы исключительно для эвристической оценки в `audit_report.md`. Это не библиотека ассетов продукта. Не встраивай их напрямую как «наши» ассеты в Figma-дизайн — они годятся только как visual reference при аннотировании находок аудита (например, через `get_screenshot` с указанием на конкретный найденный паттерн).

## 5. Иконки — статус: не определены

Иконочного набора нет. Аудит отметил мелкие/малоконтрастные иконки нижней навигации у конкурента (`audit_report.md`, экран 02) как проблему — держи это в уме как антипаттерн при выборе iconset и размеров touch target для будущей системы.

## 6. Проектная структура

Стандартная для этого репо: `directives/` = SOP (Layer 1), `execution/` = детерминированный код (Layer 2/3), `.tmp/` = регенерируемые промежуточные файлы. **Дизайн-система, когда её начнут строить в Figma, — это Layer-1-задача**: результат (ссылка на Figma-файл, набор Variables) фиксируется как deliverable, а не как файл в `.tmp/`.

---

## 7. Что реально стоит делать в Figma MCP на этой стадии проекта

1. **Мокапы фиксов из аудита.** `audit_report.md` заканчивается предложением «подготовлю отдельный набор готовых UI-исправлений (Figma-наброски)» — это готовый бэклог для `use_figma`/`figma-generate-design`: почини перекрывающийся tooltip (экран 04), увеличь target/контраст радиокнопок (экран 01), добавь empty-state подсказку (экран 02).
2. **Дизайн-система с нуля из PRD/персон** — через скилл `/figma-generate-library`, не через реверс кода (кода нет).
3. **User flow в FigJam** — в репо уже есть `Audit/user_flow.md` в виде текста; переносить в диаграмму стоит через `generate_diagram` (Mermaid → FigJam), а не вручную.
4. **Не запускай Code Connect** (`get_code_connect_map`, `add_code_connect_map`, `send_code_connect_mappings`) — нет кодовой базы, маппить не на что.

## 8. Правила именования и проверки (наследуются из `directive_figma_mcp.md`)

- Variables, слои, компоненты — имена на английском.
- Текстовый контент интерфейса — на русском (язык продукта).
- Идентифицируй объекты по Figma-ссылке или `node_id`, не угадывай.
- После любой write-операции — `get_screenshot`/`get_design_context` для визуальной проверки, не полагайся на статус «успех» без него.
- Батчи операции в один запрос к `use_figma`, не дроби на серию мелких вызовов.
